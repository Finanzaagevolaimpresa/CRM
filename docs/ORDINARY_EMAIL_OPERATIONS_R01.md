# Ordinary email — Explicit activation and bounded reception

The deployable schema is migration51 described in ORDINARY_EMAIL_MIGRATION51_R01.md. Installation of code or SQL creates no email authority, transport qualification, reception cursor or timer.

The operational CLI is `node --import tsx scripts/ordinary-email/activate.ts --plan-sha256 <reviewed-plan-sha256>`; it reads at most 16 KiB of JSON from stdin. The plan is not a credential. The responsible operator must have independently acquired the human's explicit personal email binding, initial INBOX scope, and current real SMTP/IMAP TLS and authentication evidence. Boolean fields and evidence hashes in the JSON do not constitute that authority or prove a provider qualification. They bind the reviewed act to the audited mutation. There is no public activation route or self-service approval.

The act contains the exact database, Admin user, mailbox and revision, existing mailbox responsible user, a new stream UUID, observed UIDVALIDITY/UIDNEXT, explicit NEW_FROM_ACTIVATION or EXISTING_INBOX scope, observation time, expiry and evidence references. Evidence metadata must be refreshed within five minutes of activation; the bounded reception lease is at most 31 days. NEW_FROM_ACTIVATION starts at the observed UIDNEXT minus one; EXISTING_INBOX starts at zero. The operator must not choose either scope implicitly.

A single PostgreSQL transaction locks the registered active key, both identities and the mailbox. It requires the complete schema51 ledger and exact migration hash; active Admin and responsible user; the existing canonical Register mailbox, current configuration and qualification; and an empty authority/channel/stream set. It computes separate SMTP and IMAP HMAC references from the existing process credential without outputting or saving that credential. Authority, channel, initial stream/cursor and a native minimized audit commit together. Audit failure, stale evidence, wrong target, role or hash abort every binding. Replay and concurrent re-enrollment cannot overwrite the first binding or reset a cursor. Later requalification or reconciliation requires a separate reviewed act.

Reception uses the existing `receive-once.ts --stream <uuid>` entry point. A reviewed host manifest binds it to one qualified app container, immutable image, source commit/tree, stream and activation receipt. `scripts/ordinary-email/trigger.py` runs exactly one page, verifies runtime health and identity, and records only status/counts in a private append-only journal. An exclusive host lock prevents overlap. A timeout, rejection, unexpected result or unfinished prior invocation latches future ticks before any process or provider contact. No automatic retry or journal reset is provided. A complete successful run permits the next distinct scheduled read from the durable database cursor.

The host installation is a separately authorized five-minute entry in faiadmin's existing crontab, with an outer 100-second timeout. The existing cron service must already be active; no daemon or user-lingering policy is changed. Generate the exact entry with the reviewed manifest hash and absolute release paths after deployment and activation. Preserve the existing crontab bytes and compare their hash immediately before adding the unique managed entry; a concurrent change or pre-existing entry stops installation. Log only the wrapper's minimized status to its private journal. No secrets belong in the crontab. Expiry denies further reception; renewal is a distinct qualification, never an automatic replay.

The timer does not send mail, create human sessions, approve drafts, expose an inbox, change provider flags or associate arbitrary messages. Native user context admission is still required for a received reply or attachment. Unmatched or unsupported messages stay private. A host restart or source/container replacement cannot silently resume a failed or stale trigger.

Qualification includes database tests for stale/wrong inputs, audit rollback, explicit history scopes, concurrent activation, replay and the actual native audit output. Eight synthetic process tests cover the trigger's exact command, bounded output, runtime drift, timeout and durable failure latch. Windows test adaptation simulates POSIX file flags only in tests; Linux CI exercises the real private-file checks. No real message is sent by these qualifications.
