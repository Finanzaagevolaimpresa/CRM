# N01 — Website lead containment and atomicity

The existing `POST /api/integrations/website/leads` endpoint is dormant by default. `WEBSITE_LEAD_MODE` accepts only `disabled`, `shadow`, or `legacy`; missing and unknown values (including `v2`) are disabled. Examples never activate the endpoint.

- **disabled** returns a uniform `503` with `Cache-Control: no-store` before authentication or body access and performs no database work.
- **shadow** authenticates with fixed-length SHA-256 digests and `timingSafeEqual`, then performs bounded (16 KiB), fatal UTF-8 JSON decoding and strict validation, but always returns `503` and performs no database work.
- **legacy** additionally requires valid bounded rate-limit configuration and an opaque `Idempotency-Key`. It is the sole writing mode and must not be enabled by deployment under N01.

Legacy uses a reusable PostgreSQL rate bucket (default documentation values: 30 requests/60 seconds). Every authenticated legacy attempt consumes quota. A versioned canonical payload hash and key digest—not the key—are stored in a durable opaque receipt. A single five-second deadline begins at route entry; the body reader, rate-limit transaction, statement/lock timeouts, business transaction, and bounded transient retries all receive only its remaining budget. The rate bucket intentionally survives a later business timeout, while the business transaction rolls back Lead, AuditLog, and receipt together. Following the N01-F architecture decision, that transaction uses `ReadCommitted`: digest-only PostgreSQL advisory locks remain the authoritative cross-process serialization for idempotency key, normalized email, and normalized phone. Duplicate selection uses a parameterized `FOR UPDATE` query before appending notes. The in-memory coordinator was removed because it could not prove correctness across replicas. Writers outside N01 that ignore advisory, row, or optimistic locking cannot be completely coordinated by this route alone. Replay returns the same receipt; changed payload returns `409`. Public responses never expose Lead IDs, Prisma errors, validation details, or PII.

Migration 32 is additive: it creates only `WebsiteLeadReceipt`, its indexes, and `WebsiteLeadRateLimitBucket`. It neither changes historical Lead/AuditLog rows nor requires PR86 to know about the new tables. Application rollback to PR86 therefore leaves dormant tables safely unused. No cleanup worker, scheduler, HMAC/v2 protocol, production activation, or cutover is part of N01.

Local tests cover mode containment, bounded streaming, the real five-second slow-body deadline, and dynamically injected retry classifications; these are not PostgreSQL runtime proof. PostgreSQL qualification is prepared in `tests/db/website-lead-n01-db.test.ts` and remains skipped outside the confirmed ephemeral environment. The existing DB runner discovers it automatically; CI provisions PostgreSQL 16 locally, applies migrations, binds the repository sentinel, and then runs synthetic-only tests for fresh/31→32 migrations, catalog constraints, five repeated rate-limit bursts, concurrency, overlapping identities, isolated-process advisory locking, external-writer row locking, conflict/replay, server-side statement timeout, fault rollback, and minimized audit metadata. A separate CI test archives the exact PR86 commit, builds and starts it against schema 32, checks `/api/health`, and verifies that the N01 tables remain inert. None of these PostgreSQL or PR86 runtime checks is considered passed until the CI job executes successfully.
