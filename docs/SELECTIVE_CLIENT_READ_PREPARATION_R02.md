# Selective client read: local integration preparation

Historical preparation snapshot. The current integrated candidate is documented in `SELECTIVE_CLIENT_READ_R01.md`; qualification belongs to the exact candidate commit, not to this snapshot.

This branch is local preparation only, not a release candidate. The service, session exclusions and native routes are now connected in source; their database contract remains an unexecuted draft outside migrations. No application runtime, user binding, recipient, grant or production feature has been activated. The existing full-client `ClientReadGrant` is neither migrated nor treated as a selected-field grant.

The current preparation contains a closed scalar catalogue (`displayName`, `type`, `status`), a client-specific HMAC domain, exact preview and grant validation, plus four draft persistence models. The separate user generation invalidates client decisions on identity/role/explicit-permission changes without inheriting project, lead or email authority. Client lifecycle changes use the existing record generation. A revoked or expired selection remains an ordinary-access exclusion.

Central access-control functions recognize this exclusion before broad roles, assignment or a full-client grant. An identifier-only loader now participates in session admission and fresh actors for legacy actions. It derives client, company, person, converted-lead, project/service, finance, document, practice, communication and audit exclusions. Shared finance resources are restricted without pulling other clients or their services into the selection. UUID and text resource identifiers remain separate; only audit exclusions combine domains. This graph is not a complete authorization boundary by itself: the remaining path audit and database race tests are required.

The client-specific service implements personal authority, current session and identity checks, exact preview, enforced step-up, confirmation/revocation, immutable command/history/audit and receipt recovery after an uncertain response, bound to the command's client. Native forms and `/shared-clients` routes use that service. Selection is read-only and limited to the three named scalar fields; companies, people, documents and other operations are separate residual increments. These routes have passed typechecking but have not yet been exercised in a native browser.

The current integration also excludes selected clients from ordinary lists and full-client perimeter management, assignment exception counts and pages, company referents, AI requests/notifications and dashboard previews. The mutation guards check direct client/company contexts as well as linked project, service, contract, offer and document contexts. Legacy company/project creation now checks a fresh actor and persists its audit in the same transaction. Technical-practice reassociation checks both the old and proposed client. None of these source changes constitutes PostgreSQL concurrency qualification.

`ops/drafts/selective-client-read-r01.sql` is deliberately outside `prisma/migrations`. It requires the exact completed schema56 predecessor and its checksum. It adds an initially empty authority, grant, immutable command and revision history, restrictive relationships, monotonically increasing generations and deferred checks tying current grant, command, history and minimized audit to the same transaction. It creates no authority, recipient or grant and has not been executed against any database.

The Prisma datamodel is validated syntactically. PostgreSQL behavior, migration preservation, failure injection, enrollment and concurrency remain unqualified until the completed increment is tested in the authorized CI environment. The integrated preparation passed 149 local pure regression tests, full typecheck and full lint. Identifier-graph tests use an in-memory predicate adapter; all fixtures are synthetic. These tests are not database, native browser or application-build qualification, and they do not establish transactional race safety.
